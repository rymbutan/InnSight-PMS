# 3D Room Simulation — Inspection Case Study Design Spec

Source: `Changes to be made in the System.pdf`, section 3 ("3D Room Simulation
Gameplay Mechanics"), the third and largest of the document's three
sub-projects. Sub-projects 1 (Reservation & Dashboard) and 2 (Walk-Ins &
Amenities) are complete.

The panel asks for two things: **remove the mini-games**, and replace them with
a simulation that "provide[s] students with a booking number, guest details, and
special requests to guide their evaluation of the room" — transitioning "from a
simple gamified bed-making task to a procedural, analytical case study."

The annotated screenshot on page 3 marks the room geometry "retain layout". The
room stays; the task loop built on top of it goes.

## What actually changes, conceptually

Today the student *performs* work and is graded on execution: make the bed,
vacuum the carpet, restock the minibar, across 7–13 stations. The new experience
hands them a room **already turned over by someone else** plus a clipboard, and
grades their **judgment**: is this room correct *for this booking*?

That distinction is the whole point of the redesign, and it is what the two
lead defect types in the source document encode:

- Two twin beds is not a defect. Two twin beds **for a couple** is.
- Two bath towels is not a defect. Two bath towels **for a family of four** is.

Neither is detectable by looking at the room alone — the student must read the
booking and reason from it. A pure spot-the-difference game would teach pattern
matching; this teaches the actual competency, which is checking a room against
what was sold. It also defeats the degenerate strategy: you cannot click every
object, because flagging a correct object costs you.

## Architecture

New module `web/src/sim/inspection/`:

| File | Responsibility |
|---|---|
| `caseFile.js` | Builds one coherent case: booking + which defects are injected |
| `defects.js` | The six defect categories as data — predicate, anchor, why, feedback |
| `Clipboard.jsx` | The booking panel the student consults |
| `FlagMenu.jsx` | The "what's wrong here?" categorisation control |
| `InspectionShift.jsx` | Orchestrates the room, the clipboard, flagging, and submission |
| `inspectionScore.js` | Pure scoring — React-free, unit-testable |

**Reused unchanged** (the "retain layout" instruction): `roomLayouts.js`
furniture data and the `.glb` assets, `RoomFreeRoam`'s camera / collision /
pointer-arbitration, `modelSizes.js`, `Assessment.jsx`'s Did+Why rubric,
`trainingLog.js` submission.

**Removed:** the `CATALOG` station loop in `CleaningGame.jsx` and all thirteen
task components (`BedMaking3D`, `Bathroom3D`, `Minibar3D`, `Ac3D`, `Linen3D`,
`Vacuum3D`, `Inspection3D`, `LostFoundGame`, `GuestRequestGame`, and the four
in `extraTasks.jsx`), plus `mechanics.jsx` and `taskScore.js` if nothing else
consumes them after the cut. Deleting rather than orphaning is deliberate: the
panel asked for removal, and several thousand lines of unreachable simulation
code is a liability in a codebase that will be read as part of a defence.

## The case file

Generated per run. Fields mirror what `services/reservation` already stores, so
the Housekeeping path can populate them from a real reservation:

```
{ confirmationNumber, guestName, adults, children, pax,
  roomTier, nights, arrival, specialRequests, injected: [defectId] }
```

**Coherence is enforced, not hoped for.** A case is generated by first choosing
the booking, then selecting only those defects whose `appliesTo(caseFile)`
predicate holds. An Amenity Math Error cannot be injected into a
single-occupancy booking, because there is no shortfall to detect. This is the
difference between a case that teaches and a case that is merely random.

Two to four defects are injected per run out of six, so repeat plays differ and
memorising one room's answers does not transfer.

## The six defects

Each is a data record: `{ id, category, title, appliesTo(c), anchor, why,
feedback, apply(layout, c) }`.

| id | What is wrong | Only detectable via booking? |
|---|---|---|
| `room_mismatch` | Two twin beds for a couple; no welcome amenity; single-occupancy toiletries | **Yes** |
| `amenity_math` | Towels/soap fewer than the party size | **Yes** |
| `blocked_path` | Sofa or luggage rack blocking the route to the bathroom or exit | No |
| `lingering_equipment` | Vacuum, mop bucket or rags left out; cleaning chemicals beside guest toiletries | No |
| `lived_in` | Bed unmade, curtains left haphazard, used amenities remaining | No |
| `incomplete_stock` | Minibar/snack tray empty — no items, no price list, no restock indicator | No |

**Asset constraint, stated honestly:** the model library
(`web/public/models/`) has a `twin` bed, `towel`/`towelstack`, `sofa`,
`curtain`, `minibar` and `vanity` — so mismatch, amenity math, blocked path,
lived-in and incomplete stock can all be expressed with real furniture. It has
**no** vacuum, mop bucket, cleaning-rag or chemical-bottle model. Those props
are drawn with primitives (`RoundedBox`/cylinder), exactly as the current
`Inspection3D` already draws its lamp/trash/pillow/card. Commissioning new
`.glb` assets is out of scope; if the panel wants photoreal cleaning equipment
later, only the render function of that one defect changes.

## Interaction

1. **Arrive.** The clipboard opens on entry: confirmation number, guest name,
   party composition, nights, and any special requests. It stays reachable on a
   key/button throughout — the student is meant to re-read it, not memorise it.
2. **Walk the room.** Free-roam movement and look, unchanged from
   `RoomFreeRoam`. Inspectable objects highlight on hover.
3. **Flag.** Clicking an object opens the flag menu: the six categories plus
   "This is correct — no issue". Choosing a category records both halves of the
   rubric at once:
   - correct object **and** correct category → Did ✓, Why ✓
   - correct object, wrong category → Did ✓, Why ✗ (they saw it but
     misdiagnosed it — the feedback line explains the distinction)
   - clean object flagged as a defect → **false positive**
4. **Submit.** "Finish inspection" ends the run; leaving early submits what was
   found, as the shift flow already does.

Re-flagging an object already resolved is a no-op, never a second penalty —
the existing `slipOnce` convention.

## Scoring

`inspectionScore.js` is pure and unit-tested. Per injected defect, one
Assessment item:

- found + correctly categorised → `procedure: GOOD`, `understanding: GOOD`
- found + miscategorised → `procedure: GOOD`, `understanding: ISSUES` + feedback
- missed → `procedure: ISSUES`, `understanding: null`

Plus one **inspection precision** item covering false positives: `GOOD` at zero,
`ISSUES` at one or two, `SKIPPED`-equivalent failure beyond that. Precision is
scored as its own line rather than folded into each defect, because "missed a
real fault" and "condemned a clean room" are different professional failures and
a supervisor would coach them differently.

The existing `computeVerdict` in `Assessment.jsx` consumes these unchanged.

## Booking data source

- **Training page** — synthetic cases from `caseFile.js`. Control over the
  injected defects is the entire teaching mechanism, so practice cases must be
  generated, and the four practice rooms have no reservation anyway.
- **Housekeeping page** — the room being inspected is real, so its guest name,
  party composition, special requests and confirmation number come from that
  room's reservation when one exists, with the defects still injected
  synthetically. Falls back to a synthetic booking when the room is vacant.

The reservation service already exposes everything needed (`guestName`,
`adults`, `children`, `specialRequests`, `confirmationNumber`); this is an
integration, not new data modelling.

## Backend change required

`services/auth/src/routes/training.routes.js` holds an allow-list:

```js
const ACTIVITIES = ['TURNOVER', 'GUEST_SERVICE', 'LOST_FOUND'];
const act = ACTIVITIES.includes(activity) ? activity : 'TURNOVER';
```

Unknown activities are **silently coerced to `TURNOVER`**, so without a change
every inspection run would be mislogged as a turnover and quietly corrupt the
instructor's competency summary. `INSPECTION` is added to the allow-list.

**Ruling on competency aggregation:** the summary endpoint splits room-tier
mastery (`tiers`, currently `TURNOVER` only) from other activities
(`activities`). `INSPECTION` is treated as **tier-based**, joining `TURNOVER` in
`tiers`, because it is now *the* room competency and is performed against a room
tier. Routing it to `activities` instead would leave `competent` — which
requires every tier ≥85 — permanently unreachable for any student who only ever
does the new activity. Historical `TURNOVER` rows stay valid; the summary keeps
the best score per tier, so old data neither blocks nor inflates the new.
The `roomTier` field continues to carry the tier name.

## Testing

- `caseFile` — a generated case never injects a defect whose `appliesTo` is
  false; party size and the injected set are always mutually consistent;
  injected count stays within 2–4; repeated generation varies.
- Each defect's `appliesTo` — boundary cases (party of 1 vs 2 vs 4).
- `inspectionScore` — the three per-defect outcomes, the precision bands, an
  all-missed run, a perfect run, and a run where every object was flagged
  (must score badly, proving the degenerate strategy fails).
- `Assessment.computeVerdict` — unchanged, but exercised with inspection items
  to confirm the contract still holds.
- Build must pass — `vite build` is the only thing that catches the broken-import
  class of bug that previously made a station silently fall back to 2D
  (`MINIGAMES_REBUILD.md`).
- After deletion: no dangling imports anywhere (`grep` for each removed module).

## Out of scope

- New `.glb` assets for cleaning equipment.
- Multi-room inspection rounds; one room per run, as today.
- Changing `Assessment.jsx`'s rubric or the training-results schema beyond the
  one allow-list entry.
